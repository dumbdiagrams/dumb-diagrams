This example shows an AWS architecture for asynchronously extracting data from
a supplied PDF with Amazon Bedrock, with two teams sharing the workflow. It
started as loose architecture notes, which a model shaped into the prompt
below; a coding agent then used that prompt to create the diagram. A few arrow
labels received small position adjustments in Studio, taking about five
seconds. The export includes those final human adjustments.

Notes can be part of the diagram itself. Ownership, ordering, retries, and
status are visible alongside the workflow, ready for a stakeholder meeting.

## The reviewed diagram

After [creating a project](../quick-start/), ask your agent to read `AGENTS.md`
and use the **Prompt** below. Switch tabs to inspect or download the editable
source and its requirements contract. The team names and extraction wording
have been anonymized; the Bedrock step is labeled **Extract data steps**.

Zoom in to read the notes, or expand the diagram for more room. Keep the
requirements file beside the `.dgm` if you validate the downloaded example
with the CLI.

The main arrows use native sequence badges, with descriptive labels kept
separate from the numbers. Dashed arrows show status reads, monitoring, and
dead-letter handling. The source also preserves the reviewed positions of
the resources, notes, and arrow labels.

The prompt describes ownership and behavior before asking for a layout.
It also gives the agent the text of each note, so important context survives
the move from meeting notes into the drawing.

## Guide the notes to the right place

Put the notes directly in your prompt, including what each one describes.
Naming a nearby resource or group gives the agent a clearer placement target.
For example, add this to a follow-up request:

```text
Keep the Ownership note above the Team X group.
Place Transport beside Shared AWS Infrastructure.
Place Ordering near the request queue and its publish arrow.
Keep Idempotency and Status beside Team X's job database and status API.
Place Reliability below the two dead-letter queues.
Leave space around the callouts so they do not cover connectors or labels.
```

In this example, callouts sit in open space around the architecture. You can
instead ask for a separate notes area, or use notes for assumptions, open
questions, and decisions you want to discuss with stakeholders. Review their
placement along with the rest of the diagram.

## Give the result a quick review

Open the downloaded `.dgm` in [Studio](../studio/). Check that the ownership
groups and sequence match your system, then adjust any arrow label or note
that needs more breathing room. This example needed only a brief label
placement pass; other prompts may need more refinement.

You can double-click a note to edit it, or use its sidebar controls for text,
theme, and font size. Save the file to keep the layout decisions with the
architecture. With a linked file in Chrome or Edge, **Auto-save is on by
default**, and valid changes from your agent appear automatically. See
[Auto-save and live file updates](../studio/#auto-save-and-live-file-updates)
for file linking and conflict handling.
